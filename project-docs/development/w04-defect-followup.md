## 为什么架构与编码仍会产生这些问题

原因是跨对象规则没有穷尽落实到每个命令及基础设施入口。设计已经要求撤权和可信引用，但编码把“创建/启用时对象须有效”复用于“撤销/清理”，又把资源依赖检查止于元数据侧表。各类正向路径独立通过，无法揭示对象生命周期的组合状态。构建摘要则分别由两个工具维护，新模块只补局部名单，遗漏根配置和后续目录；数字足够的测试不能发现清单本身的遗漏。

整改不靠增加零散 if 或承诺不再有任何 bug：在现有边界复用可信校验、区分命令意图、共用构建输入源，并把旧失败用例纳入必需集合。两项新增 HTTP 方法提升累计最低 Java 到253/25套件；构建输入负例使回执拒绝测试提升到82。旧成功、同数量但缺具名方法不能交付。

## 已落地架构调整与以后编码门槛

1. **撤销与启用分开校验。** 创建/启用检查引用当前可用；撤销检查对象真实存在、同集团、版本和操作者当前资格，不要求重新启用目标。继续复用管理事务和同事务审计。审查同类路径：普通授权DELETE、管理能力DELETE、任职DISABLED可空均已沿用撤销语义；成员DISABLED补齐。
2. **完整可信依赖。** 原生对象、所有权侧表、依赖资源及学校分别核验；模板/副本复用 PermissionReferences.resource，不建立平行算法。组织仍以 parentId＋schoolId 为依赖，成员及角色保护仍比较有效管理能力。前后变化、双方向跨集团、显式引用与无父级均进入回归。
3. **构建输入单一来源。** build-safe与login-test-context消费同一 product-inputs 清单；新增源码、删除文件、配置与锁文件变化纳入内容摘要。根配置不因位于core/sdk外而遗漏；生成物和node_modules不作为源码。清单本身纳入工具摘要，不能用人工修改成功回执或文件时间过门禁。
4. **测试覆盖状态转换。** 每次引用校验变化同时验证有效对象、停用、删除、错误类型、跨集团、恢复及清理。每次构建工具变化验证缺输入、新增输入、变化输入和生成物排除。先复现旧实现目标失败，再修复和重测；固定方法名随功能增加，真实MySQL/Servlet与整包链路都运行。

## 后续工作包约束

W05 的源绑定需核对实际集团数据库、账号、源版本和学校字段，不只核对绑定侧表。W06 的编辑、发布、重开需遍历模板/副本/图表/数据集完整依赖；本轮预览拒绝不代表编辑已完成。W07 的票据关闭、App停用和旧Session清理按撤销语义处理，身份有效性和App上限另查。W09 的任务取消、文件下载及缓存读取必须以当前修订复查，不把失效对象当成无法撤销。

本轮没有新增“组织管理员可否通过普通组织关系改变业务权限”的业务规则。现行保护明确是有效管理能力；普通业务授权仍按已确认的组织/任职绑定和状态求值。未来若增加禁止间接改变业务授权的委托规则，需产品明确其权限边界后再设计，不暗中改变现有成员管理行为。

停用全局用户及模板/副本状态由13306私有合成库的受控SQL夹具设置，生产HTTP负责预览、授权拒绝和成员撤销；不新增公开测试放行接口，不把合成副本归属设置写成W06实例化/编辑已完成。独立人工评审由用户/团队执行，开发者复核和自动验收单独记录。真实集团数据、React宿主、实际SQL/编辑/导出、生产容量和多节点撤权未包含，不承诺未实现入口无缺陷。
